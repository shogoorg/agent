# ベンチマーク: 低スペック・CPU環境における EmbeddingGemma スクリプトの検証

本ドキュメントは、低スペックなCPU環境PCにおいて測定された `app/` 配下の全スクリプトの実行時間およびメモリ使用量をまとめたレポートです。

## 1. テスト環境

| 項目 | 値 |
|---|---|
| CPU | Intel N100 (4コア, 4スレッド, AVX2対応, AVX-512非対応) |
| RAM | 3.7 GiB (+ 1.0 GiB スワップ) |
| GPU | なし |
| OS | Ubuntu 24.04.3 LTS on WSL2 (カーネル 6.6.87.2-microsoft-standard-WSL2) |
| Python | 3.12.3 |
| torch | 2.15.0 (CPU) |
| transformers | 5.22.2 |
| sentence-transformers | 6.2.0 |
| litert-lm-api | 0.19.1 |
| qdrant-edge-py | 0.9.0 |
| edgeparse | 0.3.2 |
| huggingface_hub | 2.4.0 |

## 2. 測定方法

- すべてのスクリプトは、プロジェクトルート (`embeddinggemma/`) からプロジェクト仮想環境 (`.venv`) を使用して実行しました。
- **合計時間** および **ピークメモリ**（最大常駐セットサイズ: `MaxRSS`）は `/usr/bin/time` で測定しました。
- **ステップごとの所要時間** は、スクリプトの標準出力の各行にタイムスタンプを付与することで算出しました（`python -u`、バッファリングなし出力）。連続する2行の出力間の時間差を、その間に行われた処理の所要時間としています。
- **オフライン版** (`*_off.py`) は `HF_HUB_OFFLINE=1` を指定して実行しました。**オンライン版** (`*_on.py`) はネットワーク接続がある状態で実行しました。
- 測定のためにスクリプトの変更は行っていません。
- 特記がない限り、すべてのモデルはあらかじめローカルの Hugging Face キャッシュに保存済みであり、オンライン実行時のネットワークアクセスは Hub のメタデータ確認のみとなります（マルチモーダルスクリプトのみ、小さなサンプル画像2枚のダウンロードを含みます）。
- 各構成は **1回ずつ** 実行しました。WSL2 上での実行時間は OS のページキャッシュ（直前に読み込んだモデルファイルは高速にロードされる）やネットワーク状況によって変動するため、同一スクリプトの実行間における約 ±20 秒程度の差は測定誤差の範囲内として解釈してください。

## 4. 詳細結果

### 4.1 `inference_embeddinggemma_with_sentence_transformers`

テキスト専用の EmbeddingGemma 2（ビジョンおよびオーディオエンコーダーは無効化、パラメータ数: 271,002,624、float32）。

| ステップ | off | on |
|---|---:|---:|
| Python 起動 + モデル読み込み | 58.6 s | 40.2 s |
| 3単語の埋め込みベクトル生成 | 3.3 s | 5.5 s |
| 3組の文ペアの類似度計算（プロンプトなし） | 0.7 s | 2.4 s |
| 3組の文ペアの類似度計算 (`STS` プロンプトあり) | 0.6 s | 0.7 s |
| インタプリタ終了処理（最後の出力後） | 6.4 s | 8.4 s |
| **合計** | **69.8 s** | **57.4 s** |

- モデルの読み込みが完了した後は、短い文ペアのエンコード処理は **約0.2秒** しかかかりません。
- **モデルの読み込みが合計時間の 70〜85% を占めています。** オンライン版の実行が速かったのは、オフライン版の直後に実行したためモデルファイルがすでに OS のページキャッシュに乗っていたことによるものです。

### 4.2 `multimodal_embeddinggemma_with_sentence_transformers`

ビジョンエンコーダーを有効化した EmbeddingGemma 2（オーディオエンコーダーは無効化、パラメータ数: 438,760,448、float32）。各類似度計算ステップでは、クエリ画像1枚と候補4件（画像1件＋テキスト3件）をエンコードします。

| ステップ | off | on |
|---|---:|---:|
| Python 起動 + モデル読み込み | 41.7 s | 47.9 s |
| クロスモーダル類似度計算（デフォルトの画像トークン予算） | 73.4 s | 57.0 s |
| クロスモーダル類似度計算 (`max_soft_tokens=1120`) | 319.1 s | 375.8 s |
| インタプリタ終了処理 | 19.8 s | 18.3 s |
| **合計** | **454.0 s** | **499.0 s** |

- **CPU 環境では画像エンコードが最大のボトルネックになります。** デフォルトのトークン予算でも画像2枚で約1分を要します。
- 最大予算の `max_soft_tokens=1120` を指定した場合、同ステップに **5〜6分（約5倍遅い）** かかります。
- オンライン版は GitHub から画像を取得し、オフライン版は `./assets/` から読み込みます。所要時間の差は実行ごとのばらつきの範囲内です。

### 4.3 `fine_tuning_embeddinggemma_with_sentence_transformers`

ファインチューニング済みテキストモデル、クエリ1件およびドキュメント1件。

| ステップ | off | on |
|---|---:|---:|
| Python 起動 + モデル読み込み + エンコード | 44.6 s | 38.6 s |
| インタプリタ終了処理 | 5.5 s | 4.9 s |
| **合計** | **50.1 s** | **43.5 s** |

- 類似度: 0.8493（両モード共通）。
- 処理時間のほとんどをモデルの読み込みが占めています。

### 4.4 `fine_tuning_multimodal_embeddinggemma_with_sentence_transformers`

ファインチューニング済みマルチモーダルモデル、テキストクエリ1件および `./assets/` からの画像3枚。

| ステップ | off | on |
|---|---:|---:|
| Python 起動 + モデル読み込み + エンコード | 107.3 s | 123.1 s |
| インタプリタ終了処理 | 13.9 s | 18.9 s |
| **合計** | **121.2 s** | **142.2 s** |

- 類似度: `[0.7091, 0.6116, 0.6654]`（両モード共通）。

Sentence Transformers（テキスト専用、float32）による2段階検索（カテゴリ → ドキュメント）と、LiteRT-LM CPU バックエンド上の Gemma 4 E2B による回答生成。2つのモデルが同時にメモリ上に読み込まれることはありません。

## 5. 主な知見

1. **Sentence Transformers (PyTorch) モデルの読み込みが最大の固定コスト（38〜59秒）**。テキスト専用スクリプトの場合、実際のエンコード処理は10秒未満で終わります。一方、LiteRT-LM はモデルを約1〜3秒で読み込みます。
2. **`EmbeddingGemma2_LiteRT_RAG` が最も高速かつメモリ効率の高いエンドツーエンドパイプライン**（オフラインで51秒、ピークメモリ1.46 GiB）。PDFの検索とLLMによる生成を含んでいるにもかかわらず、最良の結果を示しました。
3. **CPU 上での画像埋め込みは低速**。デフォルトのトークン予算でも画像2枚で約1分、`max_soft_tokens=1120` では5〜6分かかります。低スペックPCでは、小さめの予算（70、140、または280）を指定することを推奨します。
4. **メモリが最も逼迫する要因**。マルチモーダルスクリプトは、3.7 GiB のマシン上で 2.75〜2.89 GiB に達します。未使用のエンコーダーを無効化（`config_kwargs={"audio_config": None}`、テキスト専用の場合はビジョンも無効化）することで、メモリ消費を大幅に抑制できます。
5. **RAG の質問1件あたりのレイテンシは約5〜20秒**。その大半は Gemma 4 E2B による回答生成です。質問数を増やしても全体の所要時間は線形に増加するだけで、1回限りのモデル読み込みコストは増加しません。
6. **初回実行時はダウンロードとインデックス作成が支配的**。2回目以降のオンライン実行ではキャッシュが効くため、オフライン実行とほぼ同等の性能になります。
7. **インタプリタの終了処理に5〜20秒要する**。大きなテンソルのメモリ解放が行われるため、最後の出力が表示された後も時間を要します（合計時間にはこれも含まれています）。

## 6. 低スペックPC向けの推奨事項

- RAG 用途には **`EmbeddingGemma2_LiteRT_RAG_*.py`**（埋め込みと生成の両方に LiteRT-LM を使用）を優先してください。
- 毎回モデルの読み込みコストを払うのを避けるため、対話型ループなどを用いて複数のクエリ間でモデルをメモリに保持し続ける構成を検討してください。
- マルチモーダル処理では、`max_soft_tokens` を小さめの値に設定し、不要なオーディオエンコーダーは無効化してください。
- スワップの発生を防ぐため、マルチモーダルスクリプトを実行する前に他のアプリケーションを終了させてください。
- RAG の生成時間を短縮したい場合は、検索再現率とのトレードオフになりますが、`RETRIEVAL_LIMIT` や `CHUNK_SIZE` を小さく設定してください（`CHUNK_SIZE` を変更した場合は `db_gemma/` を再構築する必要があります）。
